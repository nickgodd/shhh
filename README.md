# shhh

Минималистичный анонимный веб-чат реального времени со сквозным шифрованием. Сервер не имеет базы данных, не сохраняет сообщения, не читает и не сохраняет IP-адреса, не пишет логи и не ставит внешних скриптов, шрифтов или трекеров.

## Возможности

- сессия существует только в памяти открытой вкладки;
- один экран создания с PoW-проверкой;
- поиск пользователя по точному 16-символьному идентификатору;
- входящие и исходящие запросы, принятие и отклонение;
- отдельные эфемерные ключи X25519 для каждого чата;
- AES-256-GCM, HKDF-SHA-256, случайный 96-битный nonce на сообщение;
- отпечаток ключа для проверки по независимому каналу;
- лимит сообщения 2048 байта, проверяемый на клиенте и сервере;
- мгновенное завершение чата у обеих сторон;
- отсутствие офлайн-очередей и доставки после отключения;
- строгий CSP и защитные HTTP-заголовки.

## Требования

- Node.js 20.11 или новее;
- актуальный браузер с Web Crypto API и поддержкой ECDH X25519;
- для production — TLS-сертификат либо HTTPS/WSS-терминация платформы Railway.

## Локальный запуск

```bash
npm install
npm start
```

Откройте:

```text
http://localhost:3000
```

`localhost` является secure context и позволяет браузеру использовать Web Crypto API. На остальных хостах приложение нужно открывать только через HTTPS.

Проверка синтаксиса:

```bash
npm run check
```

Интеграционная проверка двух клиентов, ключей, доставки сообщений и сброса состояния:

```bash
npm test
```

## Деплой на Railway

1. Создайте Railway Project из GitHub-репозитория с этим проектом.
2. Используйте builder `NIXPACKS`.
3. Start Command: `npm start` (Railway обычно определяет его из `package.json` автоматически).
4. Не задавайте `PORT`: Railway передаёт динамический порт через `process.env.PORT`.
5. После деплоя включите Public Networking и сгенерируйте HTTPS-домен.

В Railway сервер автоматически определяет платформу по переменным Railway, слушает `0.0.0.0` и порт из `PORT`. Внутренний HTTP не публикуется: Railway терминирует TLS, а браузер автоматически подключается к `wss://<host>/ws`.

Для этого приложения используйте ровно один replica: сессии и чаты находятся только в памяти процесса. Redeploy, перезапуск или масштабирование завершат активные сессии, что соответствует модели данных проекта.

## Production через встроенный TLS

PowerShell:

```powershell
$env:NODE_ENV = "production"
$env:HOST = "0.0.0.0"
$env:PORT = "3000"
$env:TLS_CERT_FILE = "C:\secure\fullchain.pem"
$env:TLS_KEY_FILE = "C:\secure\privkey.pem"
npm start
```

Без одновременно заданных `TLS_CERT_FILE` и `TLS_KEY_FILE` обычный production-сервер не запустится. Plain HTTP разрешён только на loopback для разработки, через локальный reverse proxy с `ALLOW_PLAINTEXT_LOCAL=1` или внутри Railway до его TLS-терминации.

## Production через Caddy

`Caddyfile` не включает access-логи и передаёт WebSocket-соединения в Node.js:

```text
{
	admin off
}

{$DOMAIN:localhost} {
	log {
		output discard
	}

	reverse_proxy 127.0.0.1:3000
}
```

Запуск Node.js только на loopback:

```powershell
$env:NODE_ENV = "production"
$env:HOST = "127.0.0.1"
$env:PORT = "3000"
$env:ALLOW_PLAINTEXT_LOCAL = "1"
npm start
```

В отдельном терминале:

```powershell
$env:DOMAIN = "chat.example.com"
caddy run --config .\Caddyfile
```

Внешний трафик в этой схеме — только HTTPS/WSS. Внутреннее соединение Caddy → Node остаётся на loopback. В `Caddyfile` вывод access-логов отключён.

## Криптографическая схема

### Идентификатор и ключ сессии

При создании сессии браузер получает 10 случайных байт через CSPRNG и кодирует их в 16 символов RFC 4648 base32 без padding. Перебор 80-битного пространства практически невозможен.

Одновременно браузер генерирует пару X25519:

- публичный ключ отправляется серверу и показывается в скрытом профиле;
- приватный ключ остаётся неэкспортируемым `CryptoKey` в памяти вкладки;
- сервер никогда не получает приватный ключ.

### Согласование чата

Для каждого запроса инициатор создаёт отдельную эфемерную пару X25519. При принятии запроса второй участник также создаёт отдельную пару. После обмена публичными ключами:

```text
shared = X25519(local_private, peer_public)
endpoints = sort_by_raw_public_key(session_id, public_key_32_bytes)
metadata = LP("shhh-chat-v1") || LP(chat_id) || count || LP(id) || LP(public_key) ...
salt = SHA-256(metadata)
(key, fingerprint) = HKDF-SHA-256(shared, salt, metadata || "key-and-fingerprint")
```

Оба участника сортируют одинаковый бинарный контекст по сырым 32-байтовым ephemeral-ключам, при равенстве — по ID. Длина и границы полей кодируются байтами, поэтому текстовая кодировка не влияет на KDF. Из 52 выходных байт первые 32 импортируются как nonextractable AES-256 ключ, следующие 20 форматируются как fingerprint.

После согласования ссылки на эфемерные приватные ключи удаляются из состояния вкладки. У каждого чата собственные временные ключи и собственное состояние счётчика.

### Сообщения

Каждое сообщение независимо шифруется:

```text
AES-256-GCM(
  key = chat_key,
  nonce = 96 случайных бит,
  plaintext = UTF-8(сообщение),
  aad = {v, chatId, senderId, messageId, sequence, plaintextSize}
)
```

`senderId` берётся сервером из авторизованного WebSocket-соединения, а не из присланного поля. Изменение AAD, ciphertext, nonce, номера или ID ломает GCM-аутентификацию.

Получатель отклоняет повторный или уже принятый `sequence`. Это защита от replay внутри одного чата.

### Ограничение 2 КБ

Под 2 КБ понимаются 2048 байт UTF-8, а не символы.

Клиент не шифрует сообщения больше 2048 байт. AES-GCM добавляет ровно 16 байт тега, поэтому сервер независимо проверяет:

```text
decode(ciphertext).length == plaintextSize + 16
plaintextSize <= 2048
```

Таким образом, сервер может строго проверить размер фактического шифртекста, не расшифровывая его.

### Отпечаток и MITM

Fingerprint показывается в открытом чате. Его нужно сравнить с fingerprint собеседника по независимому каналу, например при личной встрече или через уже доверенный разговор.

Сервер не доверен и может подменить публичные ephemeral-ключи. Сравнение одинаковых fingerprint у обеих сторон обнаруживает такую подмену. Без независимой сверки приложение не может гарантированно исключить MITM.

## Протокол и жизненный цикл

1. Стартовый экран получает одноразовый challenge и решает SHA-256 PoW.
2. Клиент генерирует ID, X25519-пару и открывает `/ws`.
3. По точному ID сервер возвращает только публичный ключ найденной активной сессии.
4. Запрос диалога и публичный ephemeral-ключ пересылаются без изменений.
5. После принятия сервер назначает случайный ID чата и пересылает вторые ephemeral-ключи.
6. Клиенты независимо выполняют ECDH → HKDF → AES-GCM.
7. Сервер проверяет только маршрутизацию, лимиты, принадлежность чату и размер ciphertext.
8. `chat:end` немедленно удаляет запись чата на сервере; клиенты удаляют ключ и DOM с сообщениями.
9. Закрытие WebSocket немедленно удаляет все чаты и ожидающие запросы пользователя. Неактивный ID удерживается только 8 секунд как grace-period, без чатов и очередей.
10. Если получатель офлайн, сообщение не сохраняется и не доставляется позже.

Reload не восстанавливает приватный ключ, поскольку браузерное хранилище запрещено. После reload нужно создать новую сессию.

## Защита от злоупотреблений

- PoW: SHA-256, 16 бит сложности по умолчанию, одноразовый challenge на 2 минуты и не более 5 попыток;
- поиск: локальный bucket 8 запросов с восстановлением 1 запроса за 4 секунды плюс глобальный bucket;
- запросы диалога: 3 запроса на сессию с восстановлением 1 запроса за 20 секунд плюс глобальный bucket;
- сообщения: burst 12 и восстановление 1 сообщения в секунду на сессию плюс глобальный bucket;
- лимит WebSocket frame 16 КиБ и строгая проверка полей протокола.

Ограничения используют только случайные session ID и глобальные счётчики. `remoteAddress`, заголовки `X-Forwarded-For` и любые другие IP не читаются.

PoW снижает стоимость массовых автоматических запросов, но не является полноценной CAPTCHA. Для более строгой защиты его можно заменить на Turnstile, но это добавит внешний скрипт и зависимость, поэтому в текущей версии PoW выбран сознательно.

## Что видит сервер

Сервер временно видит идентификаторы, публичные ключи, время и размер сетевых пакетов, а также публичный ciphertext. Он не видит plaintext, AES-ключи, приватные X25519-ключи и fingerprint в открытом сообщении.

В памяти сервера находятся только записи активных WebSocket-соединений, peer ID, публичные ключи, pending-запросы и пары участников чатов. После разрыва эти записи удаляются согласно жизненному циклу выше.
